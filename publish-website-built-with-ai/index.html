How to Publish a Website You Built with AI

You built a site with an AI tool. Here is how to get it online: the files you need, where to host it, what breaks after deploy, and what to check first.

To publish a website you built with an AI tool, you need two things: the actual files of the site, and a host that turns those files into a public address. For a simple page, that is a drag-and-drop upload to a static host and you have a link in minutes. For anything with a login, a database or a payment step, publishing is a longer job, because the parts that store data have to live on a server too.

This guide covers the neutral path: what you have, where it goes, what breaks, and what to check before you send the link to anyone.

First, find out what you actually built

Most people get stuck here. "A website" can mean three very different things, and each one is published differently. Before you touch a hosting service, ask your AI tool directly.

Copy this prompt into the chat where you built the project:

Describe the project you just built for me in plain language, as if I have never deployed anything. Answer these five questions, one by one: 1. Is this a static site (only HTML, CSS and JavaScript files), or does it need a server to run? 2. Does it store data? If yes, where — in the visitor's browser, or in a database? 3. Does it use any API key, password or secret? List them by name. 4. What is the exact list of files and folders I need to publish? 5. If I only had a drag-and-drop file host, would this project work? Yes or no, and why.

The answer to question 5 is the one that decides your next 20 minutes.

The fast path: a static site, online in minutes

If the AI says your project is static — HTML, CSS, JavaScript, images, and nothing else — publishing is genuinely easy and free to start.

  1. Get the files onto your computer. In a builder like Lovable, Bolt or v0, look for Export, Download or Connect to GitHub. If you built the page in a chat (ChatGPT, Claude), save the code into files yourself: index.html plus any CSS or JS files the AI gave you. The main page must be named index.html — hosts look for that name.
  2. Open the folder and double-click index.html. It opens in your browser, from your own machine. If it looks broken here, it will look broken online. Fix it now, not after deploying.
  3. Drop the folder on a static host. Netlify has a drag-and-drop deploy page, Cloudflare Pages and GitHub Pages publish from a repository, and Vercel deploys a folder or a repo. Any of them gives you a public URL on a subdomain they own.
  4. Open the URL on your phone. Not your laptop. Your phone, on mobile data. This catches the two most common problems at once: broken layout on small screens, and files that only existed on your computer.

That is it. You now have a link you can send.

What changes when the project has a login or a database

If the AI answered "no, it needs a server" to question 5, you are not publishing a page — you are running a small application. Three things come with that:

  • The data lives somewhere. Either in the visitor's browser (localStorage — simple, but the data disappears when they clear it and is not shared between devices) or in a hosted database. If it is a database, that database needs its own account, and it has its own free tier and its own limits.
  • Your secrets cannot ship in the files. API keys pasted into front-end code are visible to anyone who opens the page. They belong in the host's environment variables settings, never in the code you upload.
  • "It works in the preview" is not "it works online." Builder previews run with permissions and variables already set up for you. The public version has none of that until you configure it.

Ask the AI tool for this explicitly: "List every environment variable, API key and external service this project needs to run outside your preview. For each one, tell me where I create it and where I paste it on my host." Then do that list before deploying, not after.

Your site is live but broken. Check these first

Almost every first deploy breaks in one of five ways. In order of how often it happens:

  • Blank white page. Usually the main file is not named index.html, or you uploaded the folder that contains your project folder instead of the project folder itself.
  • Page loads, images missing. The image paths point at your computer (C:\Users\... or /Users/...) instead of a file inside the project. Images must be in the uploaded folder and referenced by relative path.
  • Styles gone, everything is plain text. The CSS file did not get uploaded, or the filename case does not match. Hosts are case-sensitive; Style.css and style.css are different files online, even though they are the same file on Windows and macOS.
  • Buttons do nothing. Open the browser console (right-click → Inspect → Console), copy the red error text, and paste it back to the AI with: "This is the error from the deployed version of the site you built. What is the exact file and line to change, and what should it say instead?"
  • It works for you, not for others. You are logged in or your browser cached an old version. Test in a private window and on a different device.

Do you need your own domain?

No, not to publish. The free subdomain your host gives you is a real, shareable, working link — fine for a portfolio piece, a demo, a test with five friends.

Buy a domain when the address is part of the message: a client project, a business page, anything you will print or put in an email signature. Connecting it is a settings screen on both sides, not a code change. Publish on the free subdomain first and confirm the site works; add the domain after.

The check before you share the link

Run this list every time, in about five minutes:

  • Opened the public URL in a private window — not the preview, not localhost
  • Opened it on a phone
  • Clicked every link and button once
  • Submitted every form once, with nonsense data, to see what happens
  • Searched the code for any API key, password or email address you did not mean to publish
  • Removed placeholder text — no "Lorem ipsum", no "Your Name Here"
  • Checked what a visitor can see or change that you assumed only you could

The last one matters most if real people are going to use it. An app that works is not the same as an app that is safe to hand out.

Frequently asked questions

Can I publish a website built with AI for free?

Yes, for a simple static site. Netlify, Vercel, Cloudflare Pages and GitHub Pages all have free tiers that give you a public subdomain. Free tiers change, so check the provider's current pricing page before you commit — and note that projects with a database or a login usually need a second service, which has its own limits.

Do I need GitHub to publish an AI-generated site?

Not for a drag-and-drop deploy of a static folder. You do need it for GitHub Pages, and it becomes very useful once you update the site regularly, because the host can re-publish automatically every time you change the code.

Why does my site work in the AI tool's preview but not after publishing?

The preview runs with environment variables, permissions and sample data already configured. The public version starts with none of that. Ask the tool to list every variable, key and external service the project needs outside the preview, then set each one in your host's settings.

What do I check before sharing the link with real users?

Open the public URL in a private window and on a phone, click every button, submit every form, remove placeholder text, and search the code for any API key or password. Then ask what a visitor could see or change that you assumed was private.

How long does it take to publish a simple AI-built page?

If it is static and already works on your computer, minutes. The time goes into fixing what breaks after deploy — wrong file names, missing images, broken paths — which is why testing locally first saves the most time.
