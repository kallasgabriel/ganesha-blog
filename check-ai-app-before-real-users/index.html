What to Check Before Real Users Open Your AI App

A plain-language, 8-point checklist for non-coders: secrets, access, errors, data and backups to verify before anyone else uses your AI-built app.

Before you let anyone else open an app that AI built for you, run eight checks: remove secrets from the code, confirm that access rules actually block people, test the paths where users do the wrong thing, see what your error messages reveal, know where the data lives, make a backup and restore it, check what you are publishing, and have one person who is not you try it. It takes about 60 to 90 minutes and none of it requires programming. The point is not to make the app perfect — it is to make sure it fails in small, recoverable ways instead of big, public ones.

Most checklists for this are written for software engineers and assume you can read a scanner report. This one assumes you built the app by talking to an AI tool, and that the AI is still available to help you fix whatever you find.

The 8 checks, in order

Do them in this order. The first three protect other people; the rest protect you.

  1. Secrets. No passwords, API keys or tokens sitting in the project files or visible in the page.
  2. Access. Someone who is not logged in — or logged in as a different person — cannot reach data that isn't theirs.
  3. Input. The app survives empty fields, very long text, weird characters and a double-click on "submit".
  4. Errors. When something breaks, the user sees a plain sentence, not a wall of technical detail.
  5. Data. You can say, in one sentence, what the app stores and where it is stored.
  6. Backup. You have a copy of the data and you have actually restored it once.
  7. What's published. You know which files and folders are public and you have looked at the live version yourself.
  8. One other human. A person who has never seen the app uses it in front of you while you stay quiet.

How do I find secrets the AI left in my project?

AI tools frequently paste a key directly into the code to make something work during the build, then never clean it up. That key can end up in your published files, where anyone can read it.

What to do, without reading code:

  • Ask your AI tool to list them for you. It knows what it wrote.
  • Search the project for the words key, token, secret, password and sk-.
  • Open the published version in your browser, right-click, choose "View page source" and search the same words.
  • If you find one: assume it is burned. Revoke it in the tool that issued it, create a new one, and ask the AI to move it into an environment variable or a server-side setting.

The rule to remember: anything in the part of the app that runs in the user's browser is public, no matter how buried it looks.

How do I know access rules actually work?

Hiding a button is not access control. The usual failure in AI-built apps is that the interface stops showing an option while the data underneath stays reachable.

Test it like this, with two browser windows side by side: one logged in as you, one in a private window logged out or logged in as a second test account. Then try, from the second window, to open the exact URL of something that belongs to the first account. Copy and paste the link. If it opens, your app is hiding things, not protecting them. Tell the AI exactly that: "A logged-out user can open /orders/14 by pasting the URL. Add a server-side check that blocks any request for a record that doesn't belong to the current user, and show me where you added it."

What breaks when a real person uses it?

You test the path you designed. Real users don't. Spend fifteen minutes doing the five things you would never do:

  • Submit the form completely empty.
  • Paste 2,000 characters into a field meant for a name.
  • Click the submit button three times fast.
  • Refresh the page in the middle of a task.
  • Press the browser's back button after saving something.

Write down what happens in each case. These five produce more fixable problems in an AI-built app than any scanner will, because they are about behaviour, not code.

What about the data and the backup?

Answer three questions out loud. What does this app store? Where does it physically live — the user's own browser, a file, a database in some service? What happens if that place disappears tomorrow?

If the data is stored locally in the browser, say so in the app itself: one line like "Your data is saved in this browser only." That single sentence prevents the most common complaint a first app receives.

Then test the restore, not the backup. Export the data, delete something real, and bring it back from the export. A backup you have never restored is not a backup — it is a file you hope is correct. If you want to practise this on a project built for it, the course walks you through building a task app with local data and a working backup.

A prompt you can paste into your AI tool

Run this in the same conversation where the app was built, so the AI has the full context:

Review the app we just built as if a stranger were about to use it with real data. Go through these six items one at a time and answer each separately: 1. List every API key, token or password that appears anywhere in this project, and say for each whether it is visible to the browser. 2. List every page or data request a logged-out user could reach by typing the URL directly. 3. Show me what the user sees when a save fails, and tell me if that message contains technical details. 4. Tell me exactly where user data is stored and what happens to it if the browser cache is cleared. 5. Name the three most likely ways this app breaks with ten simultaneous users. 6. For each problem above, give me the smallest fix, and tell me which ones I should not ship without. Do not change any code yet. Just report.

Asking for a report first matters. If you let the AI fix things while it is still listing them, you lose track of what was actually wrong.

Before and after: a real example

Before. A task app built in one afternoon. It works. The share link goes to a friend. Her first action is to click "Save" with an empty title field. The screen turns white and shows a red technical error with the name of the database table. She reloads, her earlier test task is gone, and she writes back: "I think I broke it."

After the checklist. Empty title shows "Please give the task a name." A failed save shows "Couldn't save — try again" and keeps what she typed. The database key that was sitting in the page source is revoked and replaced. The data is exported to a file, deleted and restored once, successfully. The friend's first message is now about the feature she wants next.

Same app, same afternoon of work, roughly one hour of checking.

What this checklist cannot do

It cannot tell you whether the app does what you actually meant. No tool can. If the AI misunderstood your idea, every check above still passes while the product is wrong — which is why the last item is a human who is not you, using it while you stay quiet and take notes.

It also will not make your app ready for payments, medical data or anything regulated. For those, "a beginner checked it" is not the standard, and the honest move is to get a professional review before real money or sensitive records are involved.
